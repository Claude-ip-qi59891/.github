<h2>二、出口类三参数：地区、类型、独占</h2>
<h3>地区锁定：宁窄勿宽</h3>
<p>把地区锁到单城市，好处是登录地曲线平直，坏处是资源紧张时可能无可用线路。锁到国家级，资源宽松但跨城跳变会让账号侧出现额外验证。多人共用场景建议锁到区域级（比如美西），内部再按城市分组，兼顾可用性和一致性。</p>
<p>调错的典型后果：把所有账号锁成「美国」，结果同一账号两周内跑了三个城市，验证次数翻倍。这类问题很难通过加钱解决，只能改参数。</p>
<h3>出口类型：别被标注骗</h3>
<p>类型参数只在采购侧有意义，拿到手必须复核。判定看 ASN 组织名，不看销售页。团队共用时建议把复核结果写进线路台账，新加入的组直接查表，不要各自再验一遍。</p>
<h3>独占标记：共用不等于共享</h3>
<p>「多团队共用」指的是账单和管理归口共用，不是让多个团队同时挤同一条线。每条线同一时刻只应有一个账号在线，其余排队或另分配。独占标记要写进系统，靠人记一定会破。</p>

<h2>三、会话类两参数：黏性与超时</h2>
<h3>黏性时长：600 到 1800 秒之间选</h3>
<p>黏性太短，一个页面里的多个请求会落到不同出口，出现「部分接口失败」这种怪现象；黏性太长，线路故障时切换慢，且资源占用高。演示和长连接场景取上限（1800 秒），普通操作取下限（600 秒）。</p>
<p>需要特别提醒：黏性不是永久绑定。超过时长仍会换出口，所以关键动作要放在同一段时间内完成，不要把一次演示拆成上下两个半天。</p>
<h3>空闲超时：别设得太激进</h3>
<p>设得太短（比如 30 秒），用户去倒杯水回来就要重连，重连后出口可能变化；设得太长，死连接占着资源不放。120 到 300 秒是比较稳的区间。演示场景可以直接拉到上限，反正只有一条线在用。</p>

<h2>四、隔离类三参数：目录、指纹、并发</h2>
<h3>环境目录：一号一目，不许复制</h3>
<p>每个账号一个独立的浏览器用户数据目录，路径按「团队/账号」两级命名，谁都不许把一份目录拷给两个号用。这条看着琐碎，实际是多团队场景里最容易崩的一条，因为新人上手第一反应就是复制现成目录。</p>
<h3>指纹一致性：四项必须对齐</h3>
<p>User-Agent 与系统版本、时区、语言、分辨率，这四项要和出口地区一致。其余如 Canvas、WebGL 属于加分项。团队共用时建议把固定组合做成模板，新人直接用模板，不要自己拼。</p>
<h3>单线并发上限：3 到 5 之间</h3>
<p>这个参数决定一条线最多带几个同时连接。设太高，多人协作时彼此拖慢，表现为大家同时变卡；设太低，排队严重。3 到 5 是多数家宽线路的合理区间，具体要看实测的 P95 延迟，超过阈值就往下调。</p>
<p>配合演示独占开关使用：演示前把该线并发上限临时锁为 1，演示结束再放开。这样能保证演示期间不会有人抢带宽。</p>

<h2>五、两套档位组合与上线前校验</h2>
<h3>日常协作档与演示档</h3>
<p>日常档：地区锁区域、黏性 600 秒、空闲超时 180 秒、单线并发 4、独占标记开启、目录独立、指纹严格对齐。演示档：地区锁单城市、黏性 1800 秒、空闲超时 300 秒、单线并发 1、演示独占开启。两套档位写在同一张配置表里，切换只改标识，不改结构。</p>
<h3>上线前的五项校验</h3>
<p>一是出口复核：随机抽三条线查 ASN 与类型；二是黏性验证：连续请求二十次，看出口 IP 是否在设定时长内保持不变；三是并发验证：按上限发起请求，看 P95 是否超阈值；四是目录检查：确认每个账号目录独立且无软链接指向同一路径；五是演示独占验证：开启开关后，换另一个团队的环境尝试调度，应被拒绝。</p>

<h2>常见问答</h2>
<h3>几个团队共用一批线路，怎么分才不出事？</h3>
<p>答：先按账号分，再按线路分。每个账号只属于一个团队，每条线路只服务一个账号。团队层面共享的是账单和管理权限，不是同时在线资格。这条边界一旦模糊，会话互相顶掉只是时间问题。</p>
<h3>黏性时长设成 0 会怎样？</h3>
<p>答：多数实现里 0 表示每次请求都重新选出口，结果是同一页面里的请求来自不同 IP。表现出来就是登录能过、某个接口 403，或者上传附件失败。除非你在做出口池探测，否则不要这么设。</p>
<h3>演示时要不要单独拉一条线？</h3>
<p>答：强烈建议。演示对稳定性的要求和日常完全不同，一条专职演示线的成本，远低于一次现场翻车的代价。如果预算不允许，至少用演示独占开关把现有线路锁住。</p>
<h3>参数改了要不要重新验证环境？</h3>
<p>答：出口相关参数（地区、类型、独占）改动后必须重新验证；会话类参数改动后建议抽验；隔离类参数改动后要逐号确认。最保险的做法是任何参数变更都记一条变更记录，带上时间、执行人和验证结论。</p>
